# ATDD Infrastructure Policy

Per `nw-distill` § Project Infrastructure Policy. One file per project. Apply-if-exists; write-if-absent; rewrite with `--policy=fresh`. Git history is the audit trail.

Bootstrapped: 2026-05-23 (first DISTILL — Slice 1 of `foundry-backend-mvp`).

The Architecture of Reference (port class → treatment) is unchanged here. This file specializes the concrete MECHANISM for each port in this codebase.

## Driving

| Port | Mechanism | Note |
|---|---|---|
| HTTP API (axum routes) | `reqwest::Client` against a `foundry_app::test_support::spawn_app()` helper that binds the real axum router on `127.0.0.1:0` and returns the bound `SocketAddr` | One in-process server per acceptance suite; per-scenario isolation via DB schema rotation (see Driven internal). No `WebApplicationFactory`-equivalent in Rust; bespoke `spawn_app()` is the idiom. |
| CLI (`foundry admin ...` subcommands) | `assert_cmd::Command::cargo_bin("foundry")` invoked as a subprocess from each scenario | Only used by US-06's "CLI-fallback password reset" scenario in Slice 1; expanded in later slices. |
| Docker Compose harness (US-01 only) | `std::process::Command` spawning real `docker compose -f tests/acceptance/fixtures/docker-compose.test.yml up -d` against a published-or-locally-built image | One Compose stack per `@us-01` scenario (slow: 30-60s startup). Tagged `@docker-compose` so CI can shard. See `driver.md`. |
| Multi-replica HTTP via in-process round-robin proxy (US-02 default lane, slice 3) | `reqwest::Client` against `support/round_robin_proxy.rs` (in-process axum-based proxy, ~50 LoC) fronting N `TestApp`s spawned by `support/multi_replica_harness.rs`. The proxy adds `X-Foundry-Replica` to every response so tests can introspect routing. | Per-scenario N replicas + one proxy; all share ONE per-scenario Postgres schema (matches production). Cheap (~250ms per scenario). |
| Multi-replica HTTP via real Caddy + docker-compose (US-02 production-shape lane, slice 3) | `std::process::Command` spawning `docker compose -f tests/acceptance/fixtures/slice3/docker-compose.multi-replica.yml up --scale foundry=3 -d` against a real `caddy` container + 3 published-or-locally-built foundry images. | One scenario only, tagged `@docker-compose @us-02 @manual-trigger`. ~35s per scenario; CI matrix opt-in. |
| CLI subcommand `foundry doctor backup-verify` (US-03, slice 3) | `assert_cmd::Command::cargo_bin("foundry")` subprocess invocation against a dump file produced by the per-scenario harness. | Driving adapter coverage for the doctor subcommand per RCA-fix P1 (subprocess invocation of the user-facing entry, not direct service call). |
| JSON API (`/api/v1/...`) — Feature A "Programmatic Foundry" (web-tier-extraction, US-W05a/b/c) | `reqwest::Client` against the SAME `foundry_app::test_support::spawn_app()` in-process router used for the HTML API, sending `Authorization: Bearer <jwt>` (+ JSON bodies). The `/api/v1` sub-router is `.merge()`-d into `build_router` by DELIVER. | Same in-process server + per-scenario schema as the HTML driving port; no new harness. The bearer credential is a real EdDSA JWT minted with the fixed test signing key (see Driven external). |
| Boundary guard (`cargo xtask check-arch` + `cargo-deny`) — Feature A (US-W06) | `std::process::Command` running `cargo run -p xtask -- check-arch` against the real workspace root (and, for violation scenarios, a throwaway tree copy with a planted violation, staged like `support/test_migration.rs`). | Subprocess against the source tree, NOT the foundry binary. Tagged `@boundary-guard` so CI shards it onto the lint lane (no Postgres). |

## Driven internal (real)

| Port | Mechanism | Note |
|---|---|---|
| `PgPool` (Postgres) — Slice 1 schema (workspaces, users, teams, projects, issues, bootstrap_tokens, invites, outbox, signin_attempts, tower_sessions) | **One shared `testcontainers-rs` Postgres 16 container per `cargo test` invocation**, plus **per-scenario schema** — each scenario gets `CREATE SCHEMA test_<uuid>` + `SET search_path` + run migrations. Schema dropped at scenario teardown. | Decision: shared container + per-scenario schema is the **speed-vs-isolation pivot** for Slice 1. Truncating tables is too entangled with FK cascades + outbox; transactional rollback fights tower-sessions's own transaction; fresh-DB-per-scenario costs 200ms/scenario × 25 scenarios = 5s overhead → ruled out. Per-schema rotation costs ~30ms/scenario. |
| `tower_sessions_sqlx_store::PostgresStore` | Same Postgres as above; tower-sessions's own migrator runs once per test schema | Sessions are first-class observable state in US-06; the store is real, never mocked. |
| `bootstrap_tokens`, `invites`, `signin_attempts` tables | Same Postgres | These are state surfaces the assertions read directly via a thin `tests/acceptance/support/db_introspect.rs` helper (read-only SELECTs); never used to bypass the driving port for writes. |
| Postgres advisory lock (`pg_advisory_lock(MIGRATION_LOCK_ID)`) — US-04 slice 3 | Real Postgres advisory lock observed via `foundry_store::run_migrations` / `run_migrations_from_dir`; `MultiReplicaHarness::spawn_concurrent` boots N replicas with `tokio::join_all` so the lock race is the actual production race. | Two replicas per scenario; per-scenario test migrations staged via `support/test_migration.rs` in a `tempfile::TempDir`. |
| `issue_attachments` bytea (US-11 slice 3) | Real `sqlx::PgPool` against the same per-scenario schema; uploads via real `axum::extract::Multipart`, downloads via real bytea SELECT. Round-trip integrity verified via in-memory sha256 against the uploaded bytes. | Slice-3 adds migration `0004_issue_attachments.sql`; bytea content lives in the same per-scenario schema as the rest of slice-1+2 state, so US-03's pg_dump scenario inherits attachment coverage without special wiring. |
| System `pg_dump` / `pg_restore` (US-03 slice 3) | `std::process::Command` shelling out to system `pg_dump -Fc` and `pg_restore --clean --if-exists` against the testcontainers Postgres host:port. Per-scenario second testcontainers Postgres serves as the restore target (restore is destructive — cannot reuse the shared container). | Contributor prereq: `pg_dump` / `pg_restore` on PATH (Postgres 16 client tools). Probed at suite startup via `pg_backup::probe_pg_tools_on_path()`; missing tools panic with an actionable message (no silent skip — F-004 anti-flake). |
| `machine_tokens` registry / `jti` denylist (Feature A, US-W05b, migration `0007`) | Same shared `testcontainers-rs` Postgres + per-scenario schema; the `jti`-keyed registry is a REAL table (stores no secret — only issuance/lifecycle metadata). Revoke/expire/forged paths exercise real rows. | Driven-INTERNAL (shared state), so REAL per the Architecture of Reference — never faked. DELIVER adds the migration + `Store` repo methods (`insert/find_by_jti/revoke/list/touch`). |

## Driven external / non-deterministic (fake)

| Port | Fake | Note |
|---|---|---|
| `lettre::SmtpTransport` (SMTP for email invites in US-05, password reset in US-06) | `FakeEmailSender` — in-memory `Vec<SentEmail>` exposed via `AppState::test_outbox()`; tests assert message count + headers + body fragments | Real SMTP (GreenMail/MailHog container) is on the slice-3 roadmap per `auth.md`'s contract-test note. Slice 1 uses the in-memory fake; the `FakeEmailSender` enforces the same input validation as `lettre::SmtpTransport` (assert `to`, `from`, `subject` non-empty) per the "test doubles must validate inputs" rule. |
| `tokio::time::sleep` (used by NFR-SEC-02 brute-force delay) | `FakeClock` exposed via `AppState::time` injection — production wires real `tokio::time::sleep`; tests wire a `MockClock` that records sleep durations and returns immediately | Decision: assert that the 6th attempt's recorded delay is ≥4500ms WITHOUT actually waiting 5s in CI. The latency assertion is on the recorded duration, not wall-clock. Justification: NFR-SEC-02 is a CORRECTNESS contract ("delay was scheduled"), not a wall-clock contract; wall-clock test would add 5s × N scenarios to the suite. |
| Bootstrap token generator (`rand::random` over 32 bytes) | Production randomness in tests; the assertion is on token *shape* (length, URL-safety, single-use), not on a specific value | The HMAC and SHA-256 paths are deterministic given the input; no fake needed. |
| Clock for `expires_at` (HMAC tokens, sessions, signin_attempts windowing) | Same `FakeClock` as above; production uses `std::time::SystemTime`; tests override via injection | Required so US-05's "expired token rejected" scenario can advance time without sleeping. |
| Per-replica health-state injection for US-02 "DB unreachable" scenario (slice 3) | Test-only `AppState::mark_db_unreachable()` flag (gated behind `cfg(any(test, feature = "test-hooks"))`) that causes `/readyz` to return 503 even when the real PgPool is healthy. | Strictly more honest than "drop the PgPool" since the real production replica's behaviour on DB outage is "Postgres unreachable -> /readyz 503", and we cannot reliably kill the testcontainers Postgres mid-scenario without affecting sibling scenarios. The flag is the cleanest seam. |
| Per-replica `X-Foundry-Replica` header (slice 3, US-02 introspection) | Production replicas do NOT add this header. Test-only middleware injected by `MultiReplicaHarness::spawn` adds it from `AppState::test_replica_addr` (`Option<SocketAddr>`, `None` in production binaries). | The header is a test affordance for round-robin-distribution + SSE-landing-replica assertions; production responses are unchanged. |
| Ed25519 machine-token signing keypair (Feature A, US-W05b) | A FIXED test keypair set on `AppState.machine_token_verifier` (and a `MachineTokenSigner` in the harness) at build, mirroring the fixed `session_secret` test value. The EdDSA sign/verify is REAL crypto — only the key MATERIAL is a known test fixture so scenarios can mint valid/expired/wrong-alg tokens deterministically. | Driven-external/non-deterministic CLASS (a credential secret), so the key material is a fixture — but the crypto path itself is exercised for real (alg-pin + signature verify are the behaviour under test). DELIVER adds `MACHINE_TOKEN_PUBLIC_KEYS`/`MACHINE_TOKEN_SIGNING_KEY` wiring (parallels `SESSION_SECRET`). |
| Token `exp` clock (Feature A, US-W05b expired-credential scenario) | Reuse the existing `FakeClock` (`MockClock`) to mint a token whose `exp` is already in the past, or to advance time past a live token's `exp`. | Same FakeClock seam used for session/signin-attempt windowing; no new fake. |
