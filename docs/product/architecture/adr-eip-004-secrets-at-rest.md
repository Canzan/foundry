# ADR-EIP-004: Outside credentials are sealed with AES-256-GCM under an operator-held key, bound to their row, with key ids, a rotation command and a boot key-check

## Status

Implemented (external-integration-plugins DELIVER, finalized 2026-10-27 at `8c681b2`; not yet
released). The status below stays Proposed until the user accepts it. Departures from this record
are listed in `docs/evolution/2026-10-27-external-integration-plugins.md` (Key decisions).

Proposed (2026-10-21, external-integration-plugins DESIGN). Resolves the mechanism of OD-12
(accepted: "a database dump or backup alone must not yield a usable credential; new operator-held
key setting").

## Context

- CA-4: for the first time Foundry stores outside credentials in its database: the Slack bot token
  (slice 01), the Matrix access token (04), later the webhook signing secrets (07) and OAuth client
  secrets (08). Until now every secret was an environment setting read once (ADR-002, ADR-006).
- SC-3: write-only credentials, never rendered, logged, returned, audited or in debug output.
- R8 (high, high). The instance is backed up with `pg_dump` (README); dumps leave the cluster.
- Earned Trust: a wrong or missing key must be detected at boot, not discovered as every route
  failing for 24 h and then dropping its messages.
- Dependency policy: `deny.toml` licence allow list; prefer crates already in `Cargo.lock`.
  `ring` 0.17.14 is already in the production graph (through `rustls` and `jsonwebtoken`), licence
  `Apache-2.0 AND ISC`, both allowed. No RustCrypto AEAD crate is in the lock today.

## Options considered

| Option | Dump alone yields a credential? | New crates | Rotation | Verdict |
|---|---|---|---|---|
| Plaintext columns | yes | 0 | n/a | Rejected (OD-12) |
| `pgcrypto` `pgp_sym_encrypt` in SQL | no | 0 (extension) | re-encrypt in SQL | Rejected: the key travels in every query, so it can land in Postgres logs and `pg_stat_statements` |
| RustCrypto `aes-gcm` or `chacha20poly1305` | no | about 6 (`aead`, `cipher`, `ctr`, `ghash`/`poly1305`, `universal-hash`, the crate) | as below | Viable; rejected only because `ring` gives the same with zero new crates |
| Envelope encryption (per-row data key wrapped by the operator key) | no | as chosen | rewrap keys only | Rejected for v1: tens of rows at homelab scale, so re-encrypting rows is as cheap as rewrapping keys, and envelope adds a second key type to reason about |
| External KMS or Vault transit | no | client crates, a service | managed | Rejected: new infrastructure; not every self-host has one |
| **`ring::aead` AES-256-GCM, direct, with key ids and AAD (chosen)** | no | **0** | `doctor` command | Chosen |

## Decision

1. **Setting:** `FOUNDRY_SECRETS_KEY`: 32 random bytes, base64url, generated by the operator
   (documented command). Optional `FOUNDRY_SECRETS_KEY_PREVIOUS`: a comma-separated list of retired
   keys accepted for opening only. Both are `SecretString`, never logged.
2. **Sealed format** (`SealedSecret`, an opaque byte string stored in `bytea`): version byte `1`,
   an 8-byte key id (the first 8 bytes of SHA-256 over a fixed label and the key), a fresh 96-bit
   random nonce, then ciphertext and tag. **Associated data** binds the ciphertext to where it lives:
   `foundry-secret|v1|{table}|{row id}|{column}`. A database writer who copies one row's ciphertext
   into another row gets an open failure, not another connection's credential.
3. **One seam:** a `SecretBox` (in `foundry-auth`, the crate that already owns HMAC and EdDSA;
   `ring` becomes a direct dependency there) with `seal(plaintext, aad) -> SealedSecret` and
   `open(sealed, aad) -> SecretString`. `SealedSecret` is an opaque bytes newtype in
   `foundry-core`, so services and store can carry it with no new crate edge. It implements no
   `Display`, `Debug` or `Serialize`. Only the foundry-app connect handlers call `seal`; only the
   foundry-app `ChannelFactory` and catalogue adapters, and the rotation command, call `open`. The
   plaintext exists only as `SecretString`, only inside those.
4. **Boot (wire, probe, use).** The board never goes down because of an integration secret, so only
   a malformed setting refuses start (revised after review, DD-2):
   - **refuse** (`health.startup.refused`, `probe = "secrets"`): a key present but not 32 bytes after
     decoding, or a failed seal/open self-test. This is a configuration error, and the
     OIDC / machine-key partial-config precedent applies;
   - **key-check:** `integration_key_checks` holds one sealed canary per key id ever used. The boot
     probe opens the canaries of the configured keys and compares the key ids of stored sealed
     credentials with them;
   - **start degraded:** the key is absent, or no configured key opens some stored credentials.
     The instance starts and serves the board. Every connection whose credential cannot be opened
     shows "unavailable" (copy: Upstream Issue UI-1) and admits no new connection or route write.
     `probe_failures_total{probe_name="secrets"}` increments and a warn-level
     `health.degraded probe=secrets` line names the missing key ids (never a key). The worker treats
     those credentials as `Transient(secret_unavailable)`, so connection state never flips to lost
     and no admin email is sent; their deliveries follow the 24-hour give-up;
   - key absent and no sealed credential exists: Slack and Matrix are simply not offered (K-2, K-18).
5. **Rotation** has a fixed order, so no replica ever holds only a key that cannot open the
   credentials:
   1. roll out `FOUNDRY_SECRETS_KEY = new` and `FOUNDRY_SECRETS_KEY_PREVIOUS = old` to every
      replica;
   2. run `foundry doctor rotate-secrets`, which re-seals every credential under the current key in
      one transaction, writes the new canary and reports counts;
   3. roll out without the previous key.
   During step 1, a replica still on only the old key opens everything (nothing is re-sealed yet).
   During step 3, every replica has the new key. If the order is broken, a replica that cannot open
   a credential classifies it as `Transient(secret_unavailable)` (ADR-EIP-002 decision 7): a local
   fault, never a connection refusal, so the connection is not marked lost and no admin is emailed.
   A gold test runs mixed-key replicas through a rotation.
6. **Losing the key** loses the credentials, not the data: connections show lost, an admin
   reconnects Slack (one approval) and re-enters the Matrix token.

## Consequences

- Positive: a dump, a backup or a read-only database compromise yields no usable Slack, Matrix,
  webhook or OAuth secret (OD-12, R8).
- Positive: zero new third-party crates; one seam to review. The boot key-check turns a silent
  24-hour outage into an immediate, named degradation (metric, log line, "unavailable" on the page),
  while the board stays up.
- Negative: the operator holds one more required secret once integrations are used, and must back
  it up separately from the database (documented beside `SESSION_SECRET`).
- Negative: an attacker with both the environment and the database can open everything, as with
  `SESSION_SECRET` today. Out of scope.
- Enforcement: check-arch `integrations-secret-seam` fails when `SecretBox::open` or
  `.open(` on a `SealedSecret` is called outside `crates/foundry-app/src/integrations/` and the
  `doctor` command; a gold test plants a call in a handler. Acceptance greps every page, log line,
  audit row and API answer for the planted token strings (EIP-KPI-5).
