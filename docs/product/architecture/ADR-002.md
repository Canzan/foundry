# 002 One shortcut route\, two arms by declared destination
Status: Superseded by BARE-PAGES-001

## Context

```text
GET /keyboard-help has one body today: a bare fragment. Two consumers read it. The client script fetches it and assigns it into the overlay host, so a framed document would nest a second head and body in the live page, and a shipped HTTP read asserts the body has no html wrapper. The rail link and the dashboard link NAVIGATE to the same URL, and the operator then gets that bare fragment as a whole page, in browser-default type with each key on its own line, which is what P1 must fix.
```

## Decision

```text
Keep one URL and one row source, and decide the arm from the destination the client itself declares in its Sec-Fetch-Dest request header: the document destination, which only a top-level navigation carries and page script cannot forge, answers a framed page on the shared card frame; every other declared destination and an absent header answer the bare fragment unchanged. One total private function holds the decision and answers the fragment for anything it does not recognise, and one builder over the shipped shortcut table feeds both arms through one rows partial.
```

## Alternatives

```text
Serve the framed page to everyone (rejected: the overlay would nest a document inside the live page and the shipped HTTP read would go red). Mark the FRAGMENT arm with a custom header added by the client script (rejected: the default arm becomes the page, so every client that sends no marker, including the shipped HTTP read, receives a document; the safe default must be the fragment, so the positive marker belongs on the page arm). Add a second URL for the page and repoint the links (rejected: a shipped read asserts the user menu links to this exact URL, and two URLs make two row sources to keep equal). Give the page the app shell instead of the card (rejected: the route is public and session-free by its own shipped rationale, and the shell needs a resolved nav identity, so this would change who the route serves).
```

## Consequences

```text
A client that navigates without declaring a destination keeps today's unstyled fragment: a degradation, never a refusal, and the residue is recorded with the user as its owner. The overlay fetch and every plain HTTP read are byte-unaffected. A future client that reaches the help through a mechanism declaring the document destination would hand a framed document to the overlay host, which the fragment case of the arm law and the shipped templating read are what hold. Both arms stay row-identical by construction through one builder and one partial, and the Quint model checks that identity.
```
