# ADR-004: Session Storage — Postgres (server-side rows)

## Status
Accepted — 2026-05-23

## Context

Slice 1 ships password+session authentication (US-06). We need to choose where session state lives. The choice has cascading effects on:

- Whether the app tier is stateless (multi-replica behavior — US-02).
- Whether logout / revocation works promptly (NFR-SEC-03, NFR-SEC-07).
- Whether SESSION_SECRET rotation logs everyone out (NFR-SEC-07).
- Whether we need a second stateful container (NFR-DATA-01: "all state in Postgres").
- Cookie size (browsers cap at 4KB per cookie; multi-cookie strategies are ugly).
- Per-request latency cost (cookie validation must not dominate NFR-PERF-01's budget).

Three candidates: server-side rows in Postgres, signed-and-encrypted cookies (no server state), or sidecar in-memory store (Redis / KeyDB).

## Decision

**Server-side session rows in Postgres**, managed by `tower-sessions` with `tower-sessions-sqlx-store` (Postgres backend).

- Cookie carries only the opaque session ID (32 bytes URL-safe random).
- Server-side row stores `{user_id: Uuid}` (intentionally minimal) + tower-sessions metadata + expiry.
- Lookup on every request is a PK-indexed read against the `tower_sessions` table.
- Logout deletes the row; the cookie is also cleared but the row delete is the canonical revocation.

## Alternatives Considered

### A: Signed-and-encrypted cookies (no server-side state)

Pattern: cookie contains `user_id` (and possibly more) encrypted with `SESSION_SECRET` (e.g., AES-GCM or XChaCha20-Poly1305). Server decrypts on each request; no DB lookup.

- **Pros**: Truly stateless (the cookie *is* the state). No DB row to manage. Zero session-lookup latency. No need for a session table.
- **Cons**:
  - **No revocation**: a stolen cookie is valid until expiry; "sign out" can only delete the client copy, the cookie itself remains valid if the attacker has it.
  - **SESSION_SECRET rotation logs everyone out** instantly — because all sessions are signed with the old key. NFR-SEC-07 explicitly says rotation should not require everyone to log in again.
  - **Workspace removal doesn't take immediate effect**: a user removed from a workspace continues to authenticate until the cookie expires (unless we add a revocation list, which is exactly the server-side state we were trying to avoid).
  - **Cookie size grows** if we put workspace/team memberships in it; we end up keeping it minimal and looking up memberships from the DB on every request — which is most of the cost of the server-side approach without its benefits.
- **Rejected because**: revocation and rotation both fail NFRs that explicitly forbid the failure modes.

### B: Sidecar in-memory store (Redis / KeyDB)

Pattern: session ID in cookie; server-side store in Redis. Industry standard.

- **Pros**: Sub-millisecond session lookups; well-trodden pattern; easy multi-replica.
- **Cons**:
  - **Adds a second stateful container** to the deployment. NFR-DATA-01 explicitly says all state lives in Postgres for MVP. Adding Redis breaks the "single pg_dump = everything" backup story (NFR-DATA-02, US-03).
  - **Increases NFR-DEV-01 cold-start time**: docker compose now has Postgres + Redis + Foundry. Possibly tolerable, but unnecessary.
  - **Operations surface doubles**: Redis backup, Redis upgrades, Redis CVEs, Redis tuning.
  - **The session lookup cost we'd save vs Postgres** is real (~0.5ms vs ~1ms) but well below NFR-PERF-01's 200ms budget. We're optimizing a non-bottleneck.
- **Rejected because**: violates NFR-DATA-01; adds operational complexity unjustified by the latency saved.

### C: In-memory per-replica store (no shared store)

Pattern: session stored in the writing replica's memory; sticky LB pins user to replica.

- **Pros**: Simplest; zero cost per lookup.
- **Cons**:
  - **Sticky sessions required.** US-02 AC explicitly forbids sticky-session requirements. Multi-replica rolling restarts log users out from the dying replica.
  - **Sessions die on replica restart.** No durability.
  - **Doesn't scale past one replica** for any session-using user.
- **Rejected because**: violates US-02 / NFR-AVAIL-01.

### D: Hybrid — encrypted cookie for read claims + DB lookup for revocation check

Pattern: cookie contains encrypted `{user_id, issued_at}`; server keeps a small "revoked sessions" or "user-changed-since" table; valid cookies skip DB if no revocation entry exists.

- **Pros**: Fast happy path; revocation works.
- **Cons**:
  - Two failure paths to test (cookie decrypt + revocation check); more concepts (T2 fail).
  - Still needs DB lookup for the revocation check, so the latency win is marginal.
  - We'd be reimplementing what JWT + revocation lists do, in a non-standard way.
- **Rejected because**: complexity not justified by the slice-1 problem.

## Consequences

### Positive

- **Stateless app tier**, satisfying US-02 + NFR-AVAIL-01 without sticky sessions.
- **Logout works immediately** by deleting the row.
- **SESSION_SECRET rotation does not log anyone out**, because the cookie value is opaque and validated by lookup, not by signature.
- **All state in Postgres**, satisfying NFR-DATA-01 and making `pg_dump` complete (NFR-DATA-02).
- **No second stateful container** to operate.
- **Audit-friendly**: every session is a row with `created_at`, `user_id`, `expires_at`. Operators can `SELECT user_id, count(*) FROM tower_sessions GROUP BY user_id` to see active sessions per user.

### Negative

- **One PK lookup per request** (the session ID -> session row). At Postgres native latency this is ~1ms warm. Within NFR-PERF-01 budget but non-zero.
- **`tower_sessions` table grows over time** with expired rows. Background cleanup task in `foundry-app` deletes `WHERE expires_at < now() - interval '7 days'` daily (advisory-locked so only one replica runs it).
- **`tower-sessions-sqlx-store` is a third-party crate** maintained by a small team. If it goes unmaintained, we'd swap to a hand-rolled equivalent (~200 LOC; non-blocking risk).

### Neutral

- Session cookie name `foundry_session`, value is opaque, flags per NFR-SEC-03.
- Session data is deliberately minimal: `{user_id: Uuid}`. Workspace/team memberships are resolved per request to ensure removal-from-workspace takes effect immediately.

## Verification

- NFR-AVAIL-01 test: a session set on replica A is valid on replica B with no sticky-session config.
- NFR-SEC-07 test: rotate `SESSION_SECRET`; existing sessions remain valid (verified by re-issuing a request with the same cookie after restart).
- NFR-OBS-02 test: stopping Postgres takes `/readyz` to 503; existing sessions in the field cannot validate until DB returns (acceptable; degradation is graceful, not data-loss).
- Cleanup task tested by inserting an expired row and asserting it's deleted on next run.
