# ADR-001: Cargo Workspace Shape (Five Crates)

## Status
Accepted — 2026-05-23

## Context

Foundry MVP is a single Rust binary, but the codebase needs internal structure that:

- Forbids the domain layer from importing infrastructure (sqlx, axum). A compile error must catch leaks rather than a code review.
- Stays approachable: per the taste filters, a Rust developer should grok the workspace in a day. No clever macros, no surprise crate boundaries.
- Survives slices 2-4 without re-shaping. Adding comments (slice 2), attachments (slice 3), and contributor onboarding tooling (slice 4) should add files to existing crates, not new crates.
- Compiles fast enough that a single-test loop (`cargo test -p foundry-core`) is sub-5-second.
- Has no traits introduced before two implementations exist (project constraint: no premature abstraction).

Slice 1 (US-01, US-05, US-06, US-07, US-08) needs HTTP routing, htmx rendering, sqlx persistence, session/auth, password hashing, and outbox/notify wiring.

## Decision

A Cargo workspace with **five crates**:

1. **`foundry-app`** (`[bin]` target) — composition root. axum routes, askama templates, request middleware, app-specific error type.
2. **`foundry-core`** (`[lib]`) — pure domain: `Workspace`, `Team`, `Project`, `Issue`, `User`, `DomainEvent`, value objects. No tokio, no sqlx, no axum in `Cargo.toml`.
3. **`foundry-store`** (`[lib]`) — Postgres adapter: sqlx queries, migration files in `migrations/`, repository functions returning domain types.
4. **`foundry-auth`** (`[lib]`) — security-sensitive surface: tower-sessions wiring, argon2id password hashing, HMAC token mint/verify, CSRF helpers.
5. **`foundry-realtime`** (`[lib]`) — `Publisher` (pg_notify wrapper) for slice 1; `PgListener` task and SSE handler land in slice 2.

Dependency direction:

```text
foundry-app  ---> {foundry-auth, foundry-store, foundry-realtime} ---> foundry-core
```

`foundry-core` depends on nothing in the workspace. The three middle crates do not depend on each other; cross-cutting use-cases compose them in `foundry-app` services.

Enforcement: `cargo-deny` + a small `xtask/check_arch.rs` pre-commit script that greps for forbidden imports (e.g., `use foundry_store` inside `crates/foundry-core/`).

## Alternatives Considered

### A: Single crate, modules only

A flat single-crate workspace with `mod core; mod store; mod auth; mod app;`.

- **Pros**: Simplest possible build; one `Cargo.toml`; no `pub use` ceremony.
- **Cons**: Module boundaries are not enforced — `mod core` can `use crate::store::PgPool` without a compile error. The "domain has no I/O" invariant becomes a code-review checkbox, not a build property. This is the exact failure mode that makes Rust "boring" projects accumulate hidden coupling.
- **Rejected because**: principle 11 demands enforceable architecture rules; module-only enforcement does not enforce.

### B: Three crates (`foundry-domain`, `foundry-infra`, `foundry-app`)

Collapse store + auth + realtime into one `foundry-infra`.

- **Pros**: Fewer Cargo.tomls; less workspace chrome.
- **Cons**: Auth (security-sensitive, tightly scoped) ends up next to outbox/realtime (broadcast wiring) ends up next to sqlx (DB schema). A reviewer auditing auth has to read 3x the code; a slice-3 change to S3 attachments touches the same crate as session cookies. The blast radius of unrelated changes is large.
- **Rejected because**: security-relevant code benefits from its own audit boundary; collapsing it hides cost in code review.

### C: Seven+ crates (split `foundry-app` into `foundry-web` + `foundry-services`, split `foundry-store` per-aggregate)

Maximum cohesion: one crate per concept.

- **Pros**: Each crate is tiny and single-purpose.
- **Cons**: Crate explosion. Compile times suffer (each crate adds link overhead). Cross-crate type sharing requires lots of `pub use`. Approachability fails: a new contributor must learn N crate names before contributing. Per "no premature abstraction": no slice-1 problem is being solved.
- **Rejected because**: taste filter — over-fragmentation buys nothing for slice 1.

### D: Trait-per-port abstraction (`Repository`, `Publisher`, `PasswordHasher` traits)

Hexagonal architecture with explicit port traits in `foundry-core`, adapters in infra crates.

- **Pros**: Textbook ports-and-adapters; easy to swap (e.g., in-memory test store).
- **Cons**: Each port has one implementation in slice 1; the trait adds a level of indirection (`dyn` or generic plumbing) without enabling a second implementation. Per the constraint "no traits unless slice 1 has two implementers," the upfront trait cost is unjustified. Tests for the store will use a real Postgres in a container (NFR-DEV-02) rather than a mock store.
- **Rejected for now**: introduce traits in slice 3 *if* the S3 attachment backend needs to coexist with the bytea backend. Concrete-first; abstract when a second implementer appears.

## Consequences

### Positive

- **Compile-enforced dependency direction.** `foundry-core` literally cannot import sqlx — Cargo refuses to compile.
- **Per-crate test loops are fast.** `cargo test -p foundry-core` compiles only domain code; ~1s on warm cache.
- **Security audit surface is small.** `foundry-auth` is ~500 LOC at end of slice 1; reviewable in an afternoon.
- **Slice 2 / 3 / 4 add files to existing crates.** Comments land in `foundry-core/src/issue.rs` + `foundry-store/src/issues.rs` + `foundry-app/src/routes/issues.rs`. No new crate needed.
- **Approachability**: `main.rs` reads as the system map. Five crate names match five concepts.

### Negative

- **Five `Cargo.toml` files to maintain.** Version bumps replicate across crates.
- **Cross-crate refactors require `pub` discipline.** Renaming an internal field of `Issue` is a multi-crate change (acceptable; it's the price of the boundary).
- **`foundry-realtime` is nearly empty in slice 1** (one `Publisher` struct). Justified by the slice 2 landing, but for a slice-1-only view this looks over-engineered.

### Neutral

- Workspace `[workspace.dependencies]` is used so version bumps for shared deps (`tokio`, `serde`, `uuid`) happen in one place.
- A `xtask/` crate is the standard Rust convention for repo automation (used for `cargo xtask check-arch`, `cargo xtask doc-licenses`, etc.).

## Verification

- `cargo check -p foundry-core` succeeds with no `sqlx`, `axum`, `tokio` in its dependency tree (verify with `cargo tree -p foundry-core`).
- `cargo xtask check-arch` (pre-commit + CI) fails on any forbidden `use` across crate boundaries.
- New contributor reads `crates/foundry-app/src/main.rs` and `crates/foundry-core/src/lib.rs` in 30 minutes and can describe the system. (Verified by NFR-DEV-01 timed onboarding.)
