# ADR-005: Error Type Strategy — thiserror per crate + IntoResponse adapter

## Status
Accepted — 2026-05-23

## Context

Rust error handling has many idioms. The choice for Foundry affects:

- Whether errors can be programmatically matched (e.g., distinguishing `Forbidden` from `NotFound` to return correct HTTP status).
- Whether errors carry source chains for debugging.
- Whether crate consumers can match on variants without depending on internals they shouldn't see.
- How errors flow from library crates through services to the HTTP boundary.
- Logging quality (errors should be structurally loggable, not just `Display`).
- Avoiding the "everything is `anyhow::Error`" trap that erases type information.

The candidate idioms:

1. **`thiserror` for libraries + `anyhow` for binaries** (idiomatic 2020s Rust).
2. **`anyhow` everywhere** (simplest, lossy).
3. **`eyre` + `color-eyre`** (similar to anyhow, prettier error reports).
4. **Hand-rolled `enum Error { ... }` without macros** (zero deps, more boilerplate).
5. **A single workspace-wide error type** (one enum to rule them all).

## Decision

**`thiserror` for every library crate, with a final `AppError` in `foundry-app` that implements `axum::response::IntoResponse`.** `anyhow` is used only in `main.rs` for startup-path failures where errors are terminal and we just want a panic-style backtrace.

### Per-crate error enums

```rust
// crates/foundry-core/src/lib.rs
#[derive(thiserror::Error, Debug)]
pub enum DomainError {
    #[error("invalid email address")]
    InvalidEmail,
    #[error("invalid slug: {0}")]
    InvalidSlug(String),
    #[error("title must be 1-256 chars")]
    InvalidTitle,
    #[error("illegal state transition: {from:?} -> {to:?}")]
    IllegalStateTransition { from: State, to: State },
}

// crates/foundry-store/src/lib.rs
#[derive(thiserror::Error, Debug)]
pub enum StoreError {
    #[error("not found")]
    NotFound,
    #[error("unique violation: {constraint}")]
    UniqueViolation { constraint: &'static str },
    #[error("database error: {0}")]
    Sqlx(#[from] sqlx::Error),
    #[error("migration error: {0}")]
    Migration(#[from] sqlx::migrate::MigrateError),
}

// crates/foundry-auth/src/lib.rs
#[derive(thiserror::Error, Debug)]
pub enum AuthError {
    #[error("invalid credentials")]
    InvalidCredentials,
    #[error("session expired")]
    SessionExpired,
    #[error("bootstrap token already used")]
    BootstrapTokenUsed,
    #[error("bootstrap token expired")]
    BootstrapTokenExpired,
    #[error("invite expired")]
    InviteExpired,
    #[error("csrf mismatch")]
    CsrfMismatch,
    #[error("forbidden")]
    Forbidden,
    #[error("rate limited; retry after {0:?}")]
    RateLimited(std::time::Duration),
    #[error(transparent)]
    Store(#[from] StoreError),
}
```

### The HTTP boundary type

```rust
// crates/foundry-app/src/error.rs
#[derive(thiserror::Error, Debug)]
pub enum AppError {
    #[error(transparent)]
    Domain(#[from] DomainError),
    #[error(transparent)]
    Store(#[from] StoreError),
    #[error(transparent)]
    Auth(#[from] AuthError),
    #[error(transparent)]
    Realtime(#[from] RealtimeError),
    #[error("template render: {0}")]
    Template(#[from] askama::Error),
    #[error("bad request: {0}")]
    BadRequest(String),
}

impl IntoResponse for AppError { /* see error-and-observability.md */ }
```

### Handler signature

Handlers return `Result<Html<String>, AppError>`. They use `?` to propagate; conversions happen via `#[from]` impls. The HTTP status is decided at the `IntoResponse` boundary, not by the handler.

## Alternatives Considered

### A: `anyhow` everywhere

```rust
async fn create_issue(...) -> anyhow::Result<Issue> { ... }
```

- **Pros**: Simplest. Every error fits. No conversion boilerplate.
- **Cons**:
  - **`anyhow::Error` is opaque**: you can `.downcast_ref::<StoreError>()` but only if you remember which type was source. Pattern matching on variants is gone.
  - The HTTP boundary cannot reliably distinguish `Forbidden` (return 403) from `NotFound` (return 404). We'd end up matching on `Display` strings or losing the distinction.
  - Crate consumers get one type per call: `anyhow::Result`. Tests cannot assert "this should be a `UniqueViolation`."
- **Rejected because**: the HTTP layer demands precise error mapping; `anyhow` erases the information we need.

### B: `eyre` + `color-eyre`

Same downsides as anyhow w.r.t. type erasure; main benefit is prettier reports during dev.

- **Rejected because**: solves a dev-experience problem we don't have at the cost of the same erasure.

### C: Hand-rolled `enum Error` (no `thiserror`)

```rust
pub enum DomainError {
    InvalidEmail,
    // ...
}
impl std::fmt::Display for DomainError { ... }
impl std::error::Error for DomainError { ... }
```

- **Pros**: Zero dependencies.
- **Cons**: 30+ lines of boilerplate per crate; easy to forget `source()` chains; bus-factor risk if a maintainer wonders why we didn't use the obvious crate.
- **Rejected because**: `thiserror` is a 100% derive-macro, zero-runtime-cost dep that the entire Rust ecosystem uses; not using it is contrarianism without payoff.

### D: Single workspace-wide error type

One big enum in a shared `foundry-errors` crate that all other crates use.

- **Pros**: No `From` chain through layers.
- **Cons**:
  - Couples every crate to every other crate's error variants.
  - `foundry-core` would have to know about `sqlx::Error` (variant `Sqlx(sqlx::Error)`) — which would import sqlx into core, violating ADR-001's "domain has no I/O" rule.
- **Rejected because**: directly contradicts ADR-001.

### E: `snafu`

Alternative error crate with context-attachment.

- **Pros**: Excellent context support.
- **Cons**: Smaller ecosystem than `thiserror`; learning curve for the context macro; we don't need its features at slice-1 scale.
- **Rejected because**: marginal benefit for the cost of an unfamiliar crate.

## Consequences

### Positive

- **HTTP status mapping is deterministic.** Every `AppError` variant has a known status.
- **Tests assert on variants**: `assert!(matches!(result, Err(AuthError::Forbidden)))`.
- **Source chains preserve causality.** A `tracing::error!(error = ?err)` logs the full chain.
- **Crate boundaries respected.** `foundry-core::DomainError` does not mention sqlx; the conversion to `StoreError::DomainViolation` happens at the store, and to `AppError::Domain` at the app.
- **`#[from]` impls collapse boilerplate.** A handler that does `let issue = state.store.issues.create(...).await?;` propagates `StoreError -> AppError::Store` automatically.

### Negative

- **More types to maintain** than a single `anyhow::Error`. Each new error variant is a deliberate addition.
- **`#[error(transparent)]` for wrapping** loses an opportunity to add context (a `snafu`-style strength). We accept this; if a variant needs context, we use a named variant.
- **`AppError` enum grows** as the app grows. Mitigated by per-source wrapper variants (one variant per crate, not one variant per leaf error).

### Neutral

- We use `anyhow` in `main.rs` for the startup chain (`anyhow::Result<()>`). Failures during startup are terminal; we just want a backtrace.
- Logging: errors are logged with `tracing::error!(error = ?err, "context message")`. The `?err` formatter walks the source chain.

## Verification

- A handler that returns `AuthError::Forbidden` produces a 403 response. Asserted in an axum integration test.
- A handler that returns `StoreError::NotFound` produces a 404. Asserted similarly.
- An `anyhow` import scan: `rg "anyhow" crates/` should find matches only in `crates/foundry-app/src/main.rs` (and possibly `xtask/`). Enforced by a pre-commit check.
- A new contributor reading `crates/foundry-app/src/error.rs` understands the full error -> response mapping in <5 minutes.
