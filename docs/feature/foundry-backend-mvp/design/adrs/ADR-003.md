# ADR-003: SQL Crate Choice — sqlx (confirmed)

## Status
Accepted — 2026-05-23

## Context

DIVERGE recommended `sqlx`; DESIGN wave is asked to confirm or revise with current (2026) evidence. The choice impacts:

- Developer ergonomics (writing queries, reading existing queries, onboarding cost).
- Compile-time safety (does a bad query crash at startup, at runtime, or fail to compile?).
- Build process complexity (does it require a live DB at compile time?).
- Performance under concurrent load (the NFR-PERF-01 budget includes DB roundtrip).
- License compatibility with AGPLv3.
- Maintenance health (release cadence, issue resolution, future viability).

We compare three contenders: `sqlx`, `sea-orm`, `diesel` / `diesel-async`.

## Decision

**`sqlx 0.8+`** for all Postgres access, with the `query!` and `query_as!` macros for compile-time-checked queries and the `SQLX_OFFLINE=true` build mode (cached `.sqlx/` directory) committed to the repository.

Plain SQL strings. No DSL. No ORM. The repository functions in `foundry-store` are essentially `sqlx::query_as!(IssueRow, "SELECT ... FROM issues WHERE ...", $1, $2).fetch_all(pool).await`.

This matches the DIVERGE rationale: "Plain SQL, compile-checked" beats sea-orm on T2 (concept count) and diesel on async-fit.

### Why confirm in 2026

- `sqlx 0.8` (current stable) added stable `query_as!` ergonomics, fixed several long-standing macro issues, and improved `tokio-postgres` performance.
- License is unchanged: MIT/Apache-2.0 dual.
- Maintenance: regular releases every ~2 months; >7k GitHub stars; active maintainers (Launchbadge organization).
- Production usage: used in many shipping Rust web apps (RisingWave, Lapce backend, multiple cloud control planes).

## Alternatives Considered

### A: `sea-orm`

Active-record-style ORM built on top of sqlx.

- **Pros**: Higher-level API; entity definitions in code; migration generation; some IDE-completion benefits via generated entity structs.
- **Cons**:
  - Adds the "ORM" concept (T2 fail). Contributors must learn entity definitions, `ActiveModel`, `Set`, `NotSet`, etc.
  - Generated migration code is harder to review than hand-written SQL — and SQL reviewability is *the* feature we want for a self-hosted product where operators may want to audit schema changes.
  - Pulls sqlx in transitively, so we're paying for both layers.
  - Hides the actual SQL behind a query builder; performance debugging requires turning on SQL logging and reading what was generated.
- **Rejected because**: net-negative on Approachability, T2, and operator-audit-friendliness. The ORM solves problems we don't have (cross-DB portability, polymorphic queries) at the cost of concepts contributors must learn.

### B: `diesel` / `diesel-async`

Sync-first ORM with a powerful query DSL; async support via `diesel-async`.

- **Pros**: Excellent compile-time safety (probably the best in Rust); mature; DSL prevents many classes of SQL injection by construction.
- **Cons**:
  - `diesel-async` lags `diesel` in features; async story is workable but not first-class.
  - The macro-heavy DSL (`use schema::issues::dsl::*; issues.filter(state.eq("backlog")).load(conn)`) has a high concept count and a learning curve — Approachability taste filter fails for an HTML-comfortable contributor who knows enough SQL to write a query but not Diesel's query builder.
  - Migrations use diesel-CLI's own format; not plain SQL.
  - Compile times can balloon due to macro expansion (acknowledged in the diesel community).
- **Rejected because**: async-fit and Approachability cost outweigh the safety upside. sqlx's `query!` macro provides ~90% of the same compile-time safety via "the database itself checks the SQL," at a small fraction of the DSL learning cost.

### C: Plain `tokio-postgres` (no compile-time checks)

The crate sqlx is built on.

- **Pros**: Smallest dependency footprint; no build-time DB requirement.
- **Cons**: No compile-time check whatsoever. Every typo is a runtime error. Hand-rolling row-to-struct conversion is tedious.
- **Rejected because**: we'd be reinventing sqlx's macro support; no upside to skipping.

### D: `rbatis`, `welds`, others

Newer entrants.

- **Cons**: Smaller community, less documentation, license verification needed per crate, immature feature surface for our needs.
- **Rejected because**: maturity bar (NFR-OSS criterion: 1000+ stars, regular releases, multiple maintainers) is not met.

## Consequences

### Positive

- **Plain SQL is reviewable.** Operators evaluating Foundry's schema for compliance can read `migrations/*.sql` directly. No code-gen translation.
- **Compile-time check via macros catches typos.** `cargo check` runs `EXPLAIN` (offline) or live-checks queries against the connected DB. PRs that ship broken SQL do not merge.
- **Async-native fits axum + tokio.** No `block_in_place` workarounds.
- **License-clean.** MIT/Apache-2.0 is the safest possible combination with AGPLv3.
- **Connection pool is built-in.** `PgPool` is what we already wanted; no separate `bb8` / `deadpool` choice.
- **`PgListener`** for `LISTEN/NOTIFY` is built-in — directly enables slice-2's realtime path.

### Negative

- **Build-time database** (or offline cache) is required for macro queries. Mitigated by committing `.sqlx/` to the repo (NFR-DEV-01: contributors compile against the cache without spinning up Postgres).
- **`cargo sqlx prepare --check`** must run in CI to catch "edited query without refreshing cache" PRs. This is a CI step, not invisible.
- **Manual row-to-domain mapping** in `foundry-store` (`IssueRow -> Issue`). Acceptable: it's also where we enforce the rule "domain types never see `sqlx::Row`."
- **No automatic migration code-gen.** We write migrations by hand. This is a feature (auditability) but means we cannot rely on entity-diff tooling.

### Neutral

- Queries that need dynamic shape (e.g., filter builders for search) use plain `sqlx::query` without the macro; the discipline is to use the macro everywhere it works.
- We will pin `sqlx = "0.8"` in workspace deps; bump cadence is "every minor when changelog is clean."

## Verification

- CI runs `cargo sqlx prepare --workspace --check`; PR fails if the cache is stale.
- Onboarding test (NFR-DEV-01): a contributor clones the repo and runs `cargo test` *without* a database; the build succeeds using the offline cache.
- A deliberate-typo PR (e.g., `SELECT idd FROM issues`) fails `cargo check` before CI.
