# ADR-002: Templating Engine — askama

## Status
Accepted — 2026-05-23

## Context

Foundry's frontend is htmx 2.x + alpine.js, server-rendered HTML. We need a templating crate that:

- Renders both full-page templates AND htmx-style partial fragments (a single `<li>` for an issue card, an updated state column, etc.).
- Hits NFR-PERF-01's 200ms P95 budget for server-render — ideally well under 50ms for the render step alone.
- Catches template errors at compile time, not in production (or at least in `cargo check`).
- Is familiar to web developers — most have seen Jinja or similar.
- Has a permissive license compatible with AGPLv3.
- Has a small concept footprint (T2 taste filter).
- Is actively maintained as of 2026.

The DIVERGE recommendation pre-selected `askama` but flagged "confirm in DESIGN with one paragraph of trade-off reasoning." This ADR is that confirmation.

## Decision

**`askama` (0.12+)** for all HTML rendering.

`askama` is a compile-time Jinja-like template engine: templates are parsed and codegen'd at build time into Rust functions. Each template file becomes a `struct` that implements `Template`, and `template.render()` produces a `String`.

Why it fits:

- **Compile-time check.** A typo in `{{ issue.titel }}` is a `cargo check` error. Production never sees a template error from a missing field.
- **Render speed.** No runtime parsing; rendering is essentially a series of `write!` calls. Benchmarks (mid-2020s, multiple sources) consistently show askama at the top of Rust templating speed charts — sub-millisecond for typical pages.
- **Jinja-shaped syntax.** `{% for issue in issues %}...{% endfor %}`, `{{ issue.title|escape }}`, `{% include "issue_card.html" %}`. Most web developers recognize it immediately.
- **Partial rendering is trivial.** A partial is just a separate template file. The handler picks which one based on `HX-Request` header. Reuse via `{% include %}` lets the project-board page and the SSE-pushed update render the same `issue_card.html`.
- **License**: MIT/Apache-2.0 dual.

Implementation pattern (sketch):

```rust
// crates/foundry-app/src/templates/issues.rs
#[derive(Template)]
#[template(path = "issues/board.html")]
pub struct BoardPage { pub project: Project, pub issues_by_state: BTreeMap<State, Vec<Issue>> }

#[derive(Template)]
#[template(path = "issues/_card.html")]  // partial — same file included by board.html
pub struct IssueCardFragment { pub issue: Issue }
```

A handler:

```rust
async fn list_issues(state: AppState, project_id: ProjectId, hx: HxRequest) -> Result<Html<String>, AppError> {
    let project = state.store.projects.get(&state.pool, project_id).await?;
    let issues = state.store.issues.list_by_project(&state.pool, project_id).await?;
    let html = if hx.is_htmx() {
        IssuesListFragment { issues }.render()?
    } else {
        BoardPage { project, issues_by_state: group_by_state(issues) }.render()?
    };
    Ok(Html(html))
}
```

## Alternatives Considered

### A: `maud`

Pure-Rust HTML macros: `html! { div { @for issue in issues { p { (issue.title) } } } }`.

- **Pros**: No template files; everything in Rust source; absolute compile-time safety; very fast.
- **Cons**: Designers/junior contributors who know HTML+Jinja must learn a Rust DSL. Re-arranging markup in a `maud!` block is a code change with Rust syntax errors, not an HTML edit. CSS framework integration (Tailwind class strings, alpine.js attributes) feels awkward because every attribute is a Rust expression.
- **Rejected because**: Approachability cost is real for a project that hopes to attract HTML-comfortable contributors. The Linear-feel htmx + alpine.js story relies on heavy HTML attribute usage that reads cleanly in Jinja and noisily in `maud`.

### B: `minijinja`

Runtime Jinja: parses templates at startup (or lazily); Python-Jinja-compatible feature set.

- **Pros**: True Jinja semantics including more advanced features (macros, inheritance). Template files can hot-reload in dev without recompile.
- **Cons**: Runtime parse. Template errors surface at request time, not build time. NFR-PERF-01 is achievable but loses askama's advantage. The Python-Jinja feature surface is bigger than we need — more concepts.
- **Rejected because**: T2 (concept count) and compile-time-safety beats hot-reload-in-dev. We can mitigate "recompile pain in dev" with `cargo watch` and incremental builds; askama templates are quick to recompile when only the .html changes.

### C: `tera`

Runtime Jinja-2 inspired engine; widely used.

- **Pros**: Mature, feature-rich, well-documented.
- **Cons**: Same runtime-parse downside as minijinja. Heavier dependency tree. Performance per request is good but not askama-good.
- **Rejected because**: No compile-time check; we'd lose a safety property without gaining a slice-1 capability we need.

### D: `handlebars-rust`

Logic-less template engine.

- **Cons**: Logic-less philosophy fights us when, e.g., we want to render a different `<button>` based on a user's role. Workarounds push logic into the handler (lots of pre-computation per template); we end up with shape-fitting structs that mirror the template needs.
- **Rejected because**: ergonomics for our use case are worse than Jinja-style.

### E: Server-rendered React via SSR

Considered for completeness; immediately rejected.

- **Cons**: Adds a Node toolchain (forbidden by NFR-DEV-01's "no Node toolchain"). Adds a second language. T1 (subtraction) failure.
- **Rejected because**: contradicts explicit project constraints.

## Consequences

### Positive

- Compile-time template safety means production never 500s from a renamed field.
- Render performance contributes to NFR-PERF-01 by being a near-zero component of total request time.
- Partial-rendering primitive fits htmx model perfectly: handlers branch on `HX-Request`, pick partial or full-page template.
- HTML-comfortable contributors can edit `.html` files without writing Rust DSL.
- The same `issue_card.html` partial renders for the board page AND for SSE-pushed updates (slice 2). DRY by design.

### Negative

- Adding a template requires either restarting the dev server or running `cargo watch -x run` — there is no in-process hot reload for askama (it's compile-time).
- Macros expand significantly during compile, increasing `foundry-app` build time. Mitigation: most edits don't add new templates, so incremental compile stays fast.
- Templates carry types: a refactor of `Issue` struct propagates to every template that references it. (Net positive — it's exactly the safety we want — but worth naming.)

### Neutral

- Template files live at `crates/foundry-app/templates/` (askama's default search path). `templates/issues/board.html`, `templates/_layout.html`, etc.
- We will write a small set of base templates (`_layout.html`, `_nav.html`) and have feature pages extend them via `{% extends %}`.

## Verification

- A render benchmark in CI (using `criterion`) asserts that the project-board template with 200 issues renders in <10ms median on the CI runner.
- A typo introduced into a template field name causes `cargo check` to fail.
